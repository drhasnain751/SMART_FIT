Application Workflow - Beginner's Guide

User Journey: Follow Sarah's complete experience from registration to receiving her personalized AI-generated fitness plan.
📝

Scene 1: Sarah Arrives and Registers

Sarah opens your website. Her browser loads your React application. The app immediately checks if she is already logged in by looking for a special key (authToken) in the browser's localStorage. It doesn't find one.

She sees the Login Page. Because she isn't logged in, the React Router automatically redirects her to the /login page.

She clicks "Register here". This takes her to the /register page, which shows the registration form.

Sarah fills out the form. She enters her name, email, and a password (e.g., "password123"). She clicks "Create Account".

🎨 Frontend to Backend (The First Handshake):
  • Her browser (your React app) bundles her email and password into a JSON package
  • It sends this package across the internet to a specific address on your backend server
POST /api/v1/auth/register { "email": "sarah@example.com", "password": "password123" }
🔧 Backend at Work (FastAPI):
  • Your FastAPI server receives the package
  • It checks if the email already exists in its simple database file (smartfit.db)
  • Since it's a new email, the server takes her password ("password123"), uses a powerful hashing algorithm (argon2), and scrambles it into a secure, unreadable string
  • The original password is never saved
  • It stores her email and the hashed password in the database
  • The backend sends a "201 Created" success message back to the browser
✅ Success!
  • The React app receives the success message and shows an alert saying "Registration successful! Please log in."
  • It then automatically navigates her to the login page
🔐

Scene 2: Sarah Logs In and Gets Her "Access Pass"

Sarah is on the Login Page. She enters the email and password she just created.

🎨 Frontend to Backend (Asking for the Pass):
  • Her browser sends her email and password to the backend, this time to the address: POST /api/v1/auth/token
POST /api/v1/auth/token { "username": "sarah@example.com", "password": "password123" }
🔧 Backend at Work (The Bouncer):
  • FastAPI receives the login attempt. It finds her email in the smartfit.db file
  • It takes the hashed password stored in the database
  • It uses the same hashing algorithm to check if the password she just typed ("password123") matches the stored hashed password
  • It's a match! The backend now knows she is the real Sarah
  • The backend then creates a special, temporary "access pass" called a JWT (JSON Web Token)
  • This token is like a digital ticket that says, "This is Sarah, and she is allowed access for the next 30 minutes"
  • This token is cryptographically signed with your JWT_SECRET_KEY so it cannot be faked
  • The backend sends this JWT token back to her browser
// Response from backend { "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...", "token_type": "bearer" }
✅ The Browser Saves the Pass:
  • The React app receives the JWT token
  • It immediately saves this token in the browser's localStorage under the key authToken
  • The app now knows Sarah is logged in and automatically navigates her to the homepage (/)
🤖

Scene 3: Sarah Generates Her AI Plan (Using the Access Pass)

Sarah is on the Homepage. She sees the "AI Planner" link in the header and clicks it.

She fills out the AI Planner form. She enters her age, weight, goals, and available equipment. She clicks "Generate My Plan".

🎨 Frontend to Backend (The Protected Request):
  • The React app bundles her form data into a JSON package
  • Before sending it, the app looks in localStorage, finds the authToken, and attaches it to the request in a special "Authorization" header
  • It looks like: Authorization: Bearer [the long token string]
  • It sends this protected request to the backend at POST /api/v1/generate-workout and POST /api/v1/generate-diet
POST /api/v1/generate-workout // Headers Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9... // Body { "age": 28, "weight": 70, "goal": "muscle_gain", "equipment": ["dumbbells", "barbell"] }
🔧 Backend at Work (Checking the Pass):
  • FastAPI receives the request. Before it even runs the AI logic, a "dependency" function (get_current_user) intercepts it
  • This function looks at the Authorization header, takes the JWT token, and uses your secret key to verify that it's a valid, unexpired token
  • Since the token is valid, it allows the request to proceed
  • (If there were no token or it was invalid, the backend would immediately stop and send back a 401 Unauthorized error)
🤖 The AI Engines Run:
  • The backend now runs your generator functions
  • It loads the exercise and food data from the CSV files into a Pandas DataFrame
  • It applies your rule-based logic (the "AI") to filter this data and construct a personalized workout and diet plan based on the form data Sarah submitted
  • It packages these two plans into a single JSON response
// AI Generated Response { "workout_plan": { "monday": [ { "exercise": "Barbell Bench Press", "sets": 4, "reps": "8-10", "rest": "90s" } ] }, "diet_plan": { "total_calories": 2800, "meals": [...] } }
✅ The Results Arrive:
  • The backend sends the JSON response containing the full plans back to Sarah's browser
  • Your React app receives this data, updates its state, and dynamically renders the PlanDisplay component
  • Sarah sees her personalized workout and diet in a beautifully formatted way
🎯 Complete Cycle: This entire flow, from registering to seeing a personalized plan, is a complete cycle of a modern full-stack application.

Potential Viva Questions and Answers

📚 Preparation Guide: Questions range from basic to advanced, with comprehensive answers you can adapt for your viva.
📋 Category 1: Project Overview & Architecture
Can you give a high-level overview of your project's architecture?

Answer: "Certainly. SmartFit is a full-stack web application built with a modern architecture. The frontend is a single-page application built with React, which provides a fast and interactive user experience. The backend is a high-performance API built with FastAPI in Python. The two communicate via a standard REST API. For data, I'm using a file-based SQLite database for user authentication and locally stored CSV files processed with the Pandas library for the AI-driven content generation."

Why did you choose FastAPI for the backend instead of a more traditional framework like Django or Flask?

Answer: "That's a great question. I chose FastAPI for two primary reasons. First, performance. FastAPI is one of the fastest Python frameworks available, built on async I/O, which is ideal for an API that might have to handle multiple requests, some of which could be computationally intensive like my AI plan generation. Second, FastAPI is specifically designed for building APIs and integrating with data science libraries. Its native support for Pydantic data validation and automatic OpenAPI documentation made it incredibly fast to develop and test the backend, especially for the complex data inputs required by the AI features."

Why did you decide to make the Exercise Library hardcoded on the frontend instead of fetching it from the API?

Answer: "That was a strategic project management decision. The core innovation and primary requirement of my project was the dynamic, AI-powered generation of personalized plans. I focused all my backend development effort on perfecting this complex feature, including the authentication and data processing pipelines. For the static content of the Exercise Library, using a hardcoded data file on the frontend was a form of mocking that allowed me to build the UI quickly and efficiently, without spending time on a simple CRUD endpoint that didn't contribute to the project's core AI functionality. It allowed me to deliver the most critical features robustly."

🤖 Category 2: Backend and AI Logic
You mention "AI" in your project. Are you using a trained machine learning model like a neural network?

Answer: "Initially, I considered using a deep learning model. However, I realized that the logic for creating good fitness and diet plans is highly rule-based and deterministic. So, instead of a traditional ML model, I implemented an Expert System, which is a well-established branch of AI. My 'AI' is a set of sophisticated, rule-based algorithms that I developed. It acts on a large knowledge base—the exercise and food datasets—to make intelligent decisions and generate plans that are not only personalized but also guaranteed to be safe and logical, which a 'black box' neural network might not provide."

How does your diet plan generator work? How does it decide which foods to pick?

Answer: "The diet generator is an optimization engine. It first calculates the user's daily caloric needs using the standard Harris-Benedict formula. Then, it uses a protein-focused greedy algorithm. For each meal, it first tries to fulfill the protein requirement by selecting foods from the database that have a high 'leanness score'—meaning a good ratio of protein to calories. Once the protein source is selected, it then intelligently fills the remaining calorie budget with carbohydrate and fat sources. This two-step process ensures the plan is nutritionally balanced and meets the user's primary fitness goal."

How do you ensure the user's password is stored securely?

Answer: "Security was a top priority. I am not storing passwords directly. When a user registers, their password is immediately run through the industry-standard Argon2 hashing algorithm using the passlib library. Only this irreversible, scrambled hash is stored in the database. When the user logs in, the password they enter is hashed again, and the two hashes are compared. This ensures that even if the database were compromised, the actual user passwords would remain completely secret."

# Password Hashing Example from passlib.context import CryptContext pwd_context = CryptContext(schemes=["argon2"], deprecated="auto") # Hashing password hashed_password = pwd_context.hash("password123") # Result: $argon2id$v=19$m=65536,t=3,p=4$... # Verifying password is_valid = pwd_context.verify("password123", hashed_password) # Result: True
Explain how your workout generator selects exercises for different muscle groups?

Answer: "The workout generator uses a multi-criteria filtering system. First, it filters exercises based on the user's available equipment. Then, it categorizes exercises by muscle groups (chest, back, legs, etc.). For each workout day, it selects exercises ensuring:

  • Variety: Different exercises for the same muscle group across the week
  • Progression: Mix of compound and isolation movements
  • Balance: Equal attention to opposing muscle groups (push/pull ratio)
  • Goal Alignment: Rep ranges and volume adjusted based on whether the goal is strength, hypertrophy, or endurance

The algorithm uses weighted random selection to ensure variety while maintaining exercise quality based on effectiveness scores in the database."

What is the role of Pandas in your application?

Answer: "Pandas is crucial for data manipulation in my AI generators. I use it to:

  • Load and parse large CSV files containing exercise and nutrition data
  • Filter data efficiently using boolean indexing based on user parameters
  • Perform complex aggregations like calculating macronutrient totals
  • Sort and rank exercises/foods based on multiple criteria

For example, when filtering exercises, I can do: df[(df['equipment'] == 'dumbbell') & (df['muscle_group'] == 'chest')] which is much more efficient than iterating through lists in pure Python."

🎨 Category 3: Frontend and User Experience
How does your application "remember" that a user is logged in, even after they close the browser tab?

Answer: "I'm using JWT (JSON Web Token) authentication. When a user logs in successfully, the FastAPI backend generates a signed token and sends it to the React frontend. The frontend then stores this token in the browser's localStorage. On subsequent page loads or app startups, the AuthProvider component first checks localStorage for this token. If it exists, the user is considered authenticated. This token is then automatically attached to every API request in the 'Authorization' header, allowing the user to access protected resources like the AI Planner."

// Storing token in React localStorage.setItem('authToken', response.data.access_token); // Retrieving token on app load const token = localStorage.getItem('authToken'); // Attaching to API requests headers: { 'Authorization': `Bearer ${token}` }
Your routing seems to handle logged-in and logged-out users differently. How did you implement this "protected routing"?

Answer: "I implemented that using a combination of React Router v6 and my custom useAuth hook. The main App.jsx component has a routing structure that checks the isAuthenticated state from the auth context. If a user tries to access a protected route like /ai-planner, the router first checks if isAuthenticated is true. If it is, it renders the requested page within the MainLayout. If it's false, it uses React Router's <Navigate> component to automatically redirect the user to the /login page."

// Protected Route Pattern {isAuthenticated ? ( <Route path="/" element={<MainLayout />}> <Route index element={<HomePage />} /> <Route path="ai-planner" element={<AIPlanner />} /> </Route> ) : ( <Route path="*" element={<Navigate to="/login" />} /> )}
What is React Context and why did you use it for authentication?

Answer: "React Context is a state management solution built into React that allows you to share data across the entire component tree without prop drilling. I used it for authentication because:

  • Global State: Authentication status needs to be accessible from any component (Header, Routes, Forms)
  • Avoids Prop Drilling: Without Context, I'd have to pass isAuthenticated through every component level
  • Centralized Logic: All auth-related functions (login, logout, token management) are in one place
  • Performance: Components only re-render when auth state changes

I created an AuthContext with AuthProvider that wraps my entire app, exposing isAuthenticated, login(), and logout() functions through a custom useAuth() hook."

How do you handle API errors and show them to the user?

Answer: "I have a comprehensive error handling strategy:

  • Try-Catch Blocks: All API calls are wrapped in try-catch blocks
  • Axios Interceptors: I use Axios interceptors to catch common errors globally (401, 500)
  • User Feedback: Errors are displayed using alert dialogs or toast notifications with user-friendly messages
  • Error States: Components have error states that display appropriate UI when something goes wrong
  • Logging: Errors are logged to the console for debugging in development
// Error Handling Example try { const response = await axios.post('/api/v1/generate-workout', data); setPlan(response.data); } catch (error) { if (error.response?.status === 401) { alert('Session expired. Please login again.'); logout(); } else { alert('Failed to generate plan. Please try again.'); } console.error('API Error:', error); }
What was the most challenging technical problem you faced in this project, and how did you solve it?

Answer: "The most challenging part was definitely the initial full-stack integration, specifically the series of errors related to CORS, Python dependencies, and React Context. For example, I repeatedly encountered a useAuth must be used within an AuthProvider error. I learned that this wasn't a simple bug, but a fundamental structural problem with how React Router renders components and how Context is passed down the tree.

I solved it by refactoring my App.jsx to a standard, robust pattern where a single parent component (AppRoutes) consumes the context and then handles all conditional rendering of public and private routes. This taught me a valuable lesson about the importance of a clean component hierarchy in React and understanding the component lifecycle and rendering order."

If you had more time, what is the next feature you would add to SmartFit?

Answer: "The next logical feature would be persistence and progress tracking. I would add a 'Save Plan' button that sends the generated AI plan back to the backend to be stored in the database, linked to the user's ID. Then, I would build a 'My Progress' page where the user could:

  • View their saved plans
  • Mark workouts as complete
  • Track their weight over time with charts
  • See progress photos
  • Get AI-powered recommendations based on their progress

This would close the feedback loop and make the application a true fitness companion rather than just a generator. I would also add social features like sharing plans and a community leaderboard to increase user engagement."

Answer: "If I were to rebuild SmartFit from scratch, I would make several improvements:

  • TypeScript: Use TypeScript instead of JavaScript for better type safety and developer experience
  • State Management: Implement Redux or Zustand for more complex state management beyond Context API
  • Database Design: Start with PostgreSQL and design a proper relational schema from the beginning
  • API Design: Implement GraphQL for more flexible data fetching
  • Real ML Model: Train an actual machine learning model using TensorFlow or PyTorch for more personalized recommendations
  • Microservices: Separate the workout generator and diet generator into independent microservices
  • Testing First: Follow TDD (Test-Driven Development) from the start
  • UI Framework: Use Tailwind CSS or Material-UI for consistent, professional styling
  • Mobile App: Build with React Native for cross-platform mobile support

However, for a learning project and MVP, the current architecture serves its purpose excellently and demonstrates all the core full-stack concepts."
